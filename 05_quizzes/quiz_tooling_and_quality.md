## Answers

**A1.** (b). Reusable workflows (called via `uses: ./.github/workflows/reusable.yml`) are full workflows with their own jobs, runner selection, and secrets handling. Composite actions bundle multiple steps into a single action that runs within the caller's job. Reusable workflows are better for multi-job orchestration; composite actions are better for reusable step sequences.

**A2.** OpenID Connect (OIDC) federation issues a short-lived token from GitHub's identity provider that the cloud provider (AWS, GCP, Azure) trusts. It eliminates the need for long-lived static credentials (e.g., AWS access keys) stored as secrets. Each workflow run gets a scoped, time-bound token with no plaintext secret to leak.

**A3.** (d). Environment variables are configuration, not artifacts. Artifact repositories store immutable binaries: JARs, wheels, container images, npm packages, tarballs, Helm charts.

**A4.** A snapshot (e.g., `1.0.0-SNAPSHOT`) is a mutable pre-release that can be overwritten repeatedly — used during development. A release (e.g., `1.0.0`) is immutable — once published, it cannot be replaced. Snapshots enable fast iteration; releases guarantee reproducibility.

**A5.** (a). `actions/cache@v4` is the generic caching action. Many setup actions (e.g., `actions/setup-node`) have a `cache: true` option that wraps it.

**A6.** An SBOM is a machine-readable inventory of all components (libraries, frameworks, OS packages) in a software artifact, including versions and licences. It enables rapid vulnerability response — when a CVE lands, you query SBOMs to find affected artifacts. Formats: CycloneDX, SPDX.

**A7.** (b). SLSA level 3 requires provenance to be generated by a hardened build platform (not by the user's own scripts) and to be non-forgeable — the signer is the build platform itself, not the submitter. This raises the bar against compromised developer machines.

**A8.** (b). cosign (part of Sigstore) signs artifacts using short-lived keys tied to an OIDC identity (e.g., a GitHub Actions workflow identity). The signature and identity are recorded in the Rekor transparency log. Keyless signing removes the need to manage long-lived signing keys.

**A9.** SAST (Static Application Security Testing) analyses source code for vulnerabilities without running it (e.g., SQL injection patterns, unsafe function calls). DAST (Dynamic Application Security Testing) runs the application and probes it with attack payloads (e.g., OWASP ZAP, Burp). SAST catches issues earlier; DAST catches runtime issues SAST can't see.

**A10.** A secret scanner searches code, commit history, and build logs for patterns that match credentials (API keys, tokens, private keys). It should run as a pre-commit hook (client-side), on every push (server-side), and periodically across the git history. Tools: gitleaks, trufflehog, GitHub's built-in scanning.

**A11.** (b). Dependabot compares your manifest files (`package.json`, `requirements.txt`, `go.mod`) against vulnerability databases (CVE via NVD, GitHub Advisory Database) to flag vulnerable versions and propose upgrades.

**A12.** The testing pyramid is a heuristic: many fast unit tests at the base, fewer integration tests in the middle, few slow end-to-end tests at the top. It matters in CI because it minimises feedback time — unit tests fail in seconds, E2E in minutes. Inverted pyramids (E2E-heavy) produce slow, flaky pipelines.

**A13.** (b). Sharding splits the test suite across N parallel runners, reducing wall-clock time to ~30/N minutes while running all tests. Skipping (a) loses coverage; nightly (c) delays feedback; reducing timeouts (d) causes flakes.

**A14.** Test impact analysis identifies which tests are affected by a given change (by tracing code dependencies) and runs only those. Sharding parallelises all tests. Impact analysis reduces the total work; sharding parallelises the remaining work. They compose.

**A15.** (c). ECR is AWS's container registry. npm, PyPI, and Maven Central are language-specific package registries (not container registries).

**A16.** (b). Shift-left scans on every push and PR to catch issues early; rescan deployed artifacts periodically because new CVEs are published against already-shipped versions. Single-point scans (a, c, d) miss either early feedback or post-deploy drift.

**A17.** No single individual should be able to both write code and deploy it to production unreviewed. Enforcement: required PR reviews, branch protection, approval gates before production deploys, and audit logs showing the reviewer and deployer are different identities.

**A18.** (b). A `Jenkinsfile` at the repo root using `pipeline { agent { ... } stages { ... } }` declarative syntax.

**A19.** A signed record describing how an artifact was built: source commit hash, build command, builder identity, build time, dependency SHAs. Verifiers check the attestation to confirm the artifact came from the expected source via the expected process. Formats: in-toto, SLSA provenance.

**A20.** (b). Artifact signing with verification at the deployment target is the only control that cuts the chain — even a compromised runner can't produce a signature the production environment trusts (if signing keys are kept out of the runner). (a), (c), (d) raise the bar but don't prevent a compromised runner from signing and deploying.

**A21.** `needs:` declares dependencies between jobs, allowing out-of-order and parallel execution of a DAG of jobs rather than the default sequential stage model. Used to build fan-out/fan-in pipelines.

**A22.** Mutation testing introduces small, deliberate bugs (mutants) into the code and checks whether the test suite catches them. A "killed" mutant is caught; a "surviving" mutant indicates gaps in coverage that line coverage doesn't reveal. It measures test effectiveness, not just test execution.

**A23.** (b). SOC 2 CC8.1 (change management) requires documented approval records for production changes. Enforced in CI/CD via PR review requirements, deployment approval gates, and audit logs of who approved what. (a) and (d) are controls but not CI/CD-specific.

**A24.** To guarantee reproducibility and avoid cache poisoning. Cached layers may contain stale dependencies with known CVEs, secrets leaked into intermediate layers, or builds that don't match the current source. `--no-cache` for the final release build ensures the artifact matches exactly what the Dockerfile and sources produce today.

**A25.** A golden image is a pre-built, hardened, signed base image (OS + core dependencies) that all application images FROM. Centralising the base image means security patches flow to all downstream images via one update, and vulnerability scanning happens once at the golden image level. It reduces the supply chain attack surface by replacing arbitrary public base images with a vetted, maintained internal one.
